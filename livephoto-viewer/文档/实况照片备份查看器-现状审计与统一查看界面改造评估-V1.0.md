## 一、审计结论摘要

1. **当前工具已具备"统一网格查看器"原型**，并非用户描述的"每张照片一个 HTML 需逐个打开"。现有 `build_html()` 生成的是**单个** `网页查看器/index.html`，内含所有照片的缩略图网格，悬停/点击切换封面与动图。【已验证：源码行 104-164 + EXE 复跑产物】
2. **当前工具的"动态"是 GIF，不是真实视频**。HTML 用两张 `<img>`（封面 jpg + GIF）切换显示来模拟"播放"，浏览器并不播放原始 `.mov/.mp4`，也无法真正"暂停在某个时间点"——只能切换封面/GIF 显隐。【已验证：源码 + 产物；真实视频解码能力【待验证】】
3. **当前工作流是"备份型"而非"只读浏览型"**：必须选择"输出文件夹"，默认会把原文件复制到 `原始文件/`、把视频转成 GIF（1.98 MB/段）、生成 HTML。这与用户目标"默认只读扫描、不复制、不生成 GIF"不一致。【已验证：源码 `process_directory` 行 167-233 + EXE 复跑】
4. **配对只支持"完整配对"，不识别缺失/不确定状态**：`find_live_photos()` 仅按文件名 `base.lower()` 配对，且**只返回图片和视频都存在的项**（行 61 的过滤条件）。用户目标中的"图片缺失/视频缺失/配对不确定/普通照片"四类状态当前**完全不支持**，需新增分类逻辑。【推断：源码行 46-61】
5. **配对仅依赖同名，不读取元数据**：代码无任何 EXIF/容器元数据解析，纯字符串基名匹配。【推断：源码】
6. **运行环境无可用 Python**（指向 Windows 应用商店占位符，exit 9009），但项目自带自包含绿色 EXE（PyInstaller 单文件，内置 ffmpeg + Pillow + imageio-ffmpeg），可正常运行。【已验证】
7. **可复用资产充足**：`find_live_photos / convert_to_gif / extract_cover / build_html / process_directory` 等函数均可直接复用，无需推倒重写。
8. **HEIC 与 HEVC 兼容性风险客观存在**：浏览器无法直接显示 HEIC；iPhone 实况导出的 `.mov` 常含 HEVC，部分浏览器无法解码。当前工具靠 ffmpeg 转 GIF 规避，但代价是体积膨胀。

**一句话结论**：用户想要的"统一、只读、可重选目录、分类统计、点开即播真实动态"能力，当前工具只覆盖了一部分（统一网格页）。真正缺口是**只读浏览模式 + 五态分类 + 真实视频播放**，而不是"合并多个 HTML"。推荐在现有桌面程序上做增量增强（方案 A），不要重写。

## 三、当前配对与 HTML 生成机制的代码证据

### 3.1 图片/视频配对（【推断】源码逻辑）

`find_live_photos(src_dir)`（行 46-61）：

```python
42  PHOTO_EXTS = {".heic", ".heif", ".jpg", ".jpeg", ".png"}
43  VIDEO_EXTS = {".mov", ".mp4", ".m4v"}
46  def find_live_photos(src_dir):
47      pairs = {}
49      for root, dirs, files in os.walk(src_dir):        # 递归扫描子目录
51          base, ext = os.path.splitext(f)
55          key = base.lower()                            # 仅按文件名基名配对
56          entry = pairs.setdefault(key, {"name": base})
57          if ext in PHOTO_EXTS: entry["photo_path"] = full
60          else:                 entry["video_path"] = full
61      return [v for v in pairs.values() if "photo_path" in v and "video_path" in v]
```

结论（【推断】）：
- **配对仅依赖同名基名，不读元数据**。
- **只返回"图片+视频都存在"的完整配对**；同名多候选会互相覆盖（dict 同 key 后者胜，行 56-60），**不存在"不确定"分支**。
- 支持的图片格式：`.heic .heif .jpg .jpeg .png`；视频：`.mov .mp4 .m4v`（行 42-43）。

### 3.2 单张/整体 HTML 生成（【已验证】源码 + 产物）

`build_html(output_dir, items)`（行 104-164）生成**单个** `网页查看器/index.html`：

- 行 108-114：每张照片生成一个 `.card`（封面 `<img class="cover">` + 动图 `<img class="mov">` + 标题）。
- 行 115-158：内联 CSS 网格（`grid-template-columns:repeat(auto-fill,minmax(220px,1fr))`）+ JS：悬停 `mouseenter` 加 `playing` 类、点击 `toggle` `playing`（行 146-155）。
- 行 159-164：把 `__COUNT__`/`__CARDS__` 替换后写盘。

`process_directory` 中构建 items（行 209-229）：
```python
216  "cover_rel": "thumb/" + p["name"] + ".jpg",
217  "gif_rel":   "../GIF动图/" + p["name"] + ".gif",
```
即 HTML 用**相对路径**引用 `网页查看器/thumb/*.jpg` 与同级 `../GIF动图/*.gif`。**这意味着 index.html 必须与 `GIF动图/`、`网页查看器/thumb/` 保持相对位置**，单独移动 index.html 会断链（【推断】相对路径耦合）。

> **重要更正**：用户描述"为每张照片生成单独的 HTML 需逐个打开"**与当前代码不符**。当前实现自一开始就是单一网格页。建议改造前先与用户确认：真实痛点应是"必须选输出目录、会复制原文件并生成 GIF"，而非"多 HTML"。

### 3.3 当前"动态播放"的本质（【已验证】+【待验证】）

- 动图来源是 **GIF**（`convert_to_gif`，行 76-79，ffmpeg 转码 `fps=12,scale=540:-1,loop 0`）。
- 封面来源是 **视频首帧 jpg**（`extract_cover`，行 82-84）。
- 浏览器端切换的是"封面图 ↔ GIF 图"的显隐（CSS 行 15-17），**不是播放原始视频**，也**不能真正暂停在某一帧**（GIF 是无限循环，切换只是显示/隐藏）。
- 真实视频（`.mov/.mp4`）是否被浏览器原生播放，本机**未做浏览器实测**（【待验证】）。

## 五、三种实现方案对比

> 维度定义见用户需求第六章；结论基于【推断】+ 已验证事实，凡涉及浏览器/真实视频处标注【待验证】。

### 方案 A：保留桌面程序，增加统一的本地查看界面

- 在现有 `App`（tkinter）上加"只读预览"模式：用户选**源目录**（无需输出目录），程序扫描并复用 `find_live_photos`，**扩展**为五态分类，生成**单一**预览页（复用 `build_html`，改造成支持状态标签/计数）。
- 预览页可落到临时目录（或直接用 `file://` 绝对路径指向原始文件），默认不复制、不生成 GIF；仅当浏览器无法解码原视频时，按需对个别文件调 `convert_to_gif` 做兜底（写入临时目录，不污染原始）。
- **开发量**：中（主要新增"五态分类"+ "只读预览"开关 + 状态 UI）。
- **复用度**：高（几乎全部现有函数可复用）。
- **安全性**：高（默认只读，复制/转码仅发生在临时区或用户明确导出时）。
- **是否重生成 HTML**：是，但只生成 1 个预览页（非每图 1 个）。
- **是否复制媒体**：默认否（只读）；导出模式才复制。
- **兼容性**：HEIC 用封面 jpg（已解决）；HEVC 用按需 GIF 兜底。
- **Windows 10/11 体验**：原生 EXE，双击即用，最佳。
- **维护成本**：低（同一代码库）。
- **后续扩展（批量导入/缺失检查）**：易（逻辑已在 `process_directory` 内）。

### 方案 B：每次扫描生成一个包含全部照片的统一 HTML 查看器

- 本质就是**当前 `build_html` 已做的事**（单一 index.html）。差异只在"资源组织方式"：
  - (b1) 相对路径引用输出目录（当前做法，强耦合）；
  - (b2) 复制媒体到输出目录（同当前"备份"流程，违背只读）；
  - (b3) 内联 base64（单文件自包含，但体积随照片数爆炸，不可取）。
- 若 B 仅指"生成统一 HTML"，它**已是现状**，不算新方案；真正要决断的是"是否复制/转码"与"是否只读"。
- **开发量**：低（几乎现成）。
- **复用度**：最高。
- **安全性**：取决于是否复制（b2 会改输出目录，但原始仍可不动）。
- **是否重生成 HTML**：是（每扫一次 1 个）。
- **是否复制媒体**：b2 复制，b1 不复制但依赖相对路径。
- **兼容性 / 体验 / 维护**：同 A 的预览部分。
- **局限**：纯静态 HTML 无法直接读用户任意文件夹（需文件选择或本地服务），见方案 C。

### 方案 C：独立的本地网页查看器（浏览器直接读本地文件夹）

- 用 `<input type="file" webkitdirectory>` 让用户选文件夹，文件载入浏览器内存（无服务器），前端渲染网格 + `<video>` 播放。
- **必须明确**：普通网页**不能**任意读取用户电脑目录，必须经用户主动选择（`webkitdirectory`）或借助本地辅助程序/本地 HTTP 服务。**不能假定"打开网页就能扫全盘"。**
- **开发量**：高（需写前端、处理文件选择、缩略图、视频解码、内存管理；或额外写本地服务）。
- **复用度**：低（现有 Python/ffmpeg 资产基本用不上，除非做本地服务桥接）。
- **安全性**：中（文件选择机制本身安全，但 HEIC/HEVC 仍无解）。
- **是否重生成 HTML**：否（动态生成于内存）。
- **是否复制媒体**：否（内存引用）。
- **兼容性（关键）**：
  - **HEIC**：浏览器**普遍不支持**直接显示，前端无 ffmpeg 无法转码 → 必须靠本地辅助程序预转或放弃 HEIC 缩略图（【待验证】具体浏览器支持度）。
  - **HEVC(.mov)**：Chrome/Edge/Firefox 对 HEVC 支持不一，常无法播放 → 真实动态可能失效（【待验证】）。
  - **大目录/大文件**：全部读入内存，数千张或 4K 大视频易 OOM（【待验证】）。
- **Windows 体验**：受浏览器与 codec 限制，最不稳。
- **维护成本**：高（前端 + 可能的本地服务双栈）。
- **后续扩展**：中（前端可实现，但 codec/内存坑多）。

### 对比总表

| 维度 | A（增强桌面程序） | B（统一 HTML） | C（纯网页） |
|---|---|---|---|
| 开发改造量 | 中 | 低（现成） | 高 |
| 现有代码复用 | 高 | 最高 | 低 |
| 原始文件安全/只读 | 高（默认只读） | 视资源组织而定 | 高（内存） |
| 重生成 HTML | 1 个预览页 | 1 个 | 否 |
| 复制媒体 | 默认否 | b2 复制 | 否 |
| HEIC 兼容 | ✅ 封面 jpg | ✅ | ❌ 前端无解（除非本地辅助） |
| HEVC 视频兼容 | ⚠️ 按需 GIF 兜底 | ⚠️ 同 | ❌ 浏览器常不支持 |
| 大目录/内存 | 稳（磁盘流式） | 稳 | ⚠️ 易 OOM |
| Win10/11 体验 | 最佳（原生 EXE） | 佳 | 不稳 |
| 维护成本 | 低 | 低 | 高 |
| 后续扩展难度 | 易 | 易 | 中（坑多） |

## 六、推荐方案及原因

**推荐：方案 A（增强现有桌面程序，增加"只读预览"模式），并复用方案 B 的"单一统一 HTML"作为预览载体。**

理由（不追求技术先进、不推倒重写）：

1. **用户核心痛点不是"多 HTML"，而是"必须选输出目录 + 复制原文件 + 生成 GIF"**。方案 A 直接消除这一点：新增"只读预览"开关，用户只选源目录即可。
2. **复用度最高、风险最低**：`find_live_photos / convert_to_gif / extract_cover / build_html / App` 全部可复用，不重写，不破坏已分发 EXE 的既有能力（README 明令"任何改动前先确认不会破坏 EXE 可用性"）。
3. **HEIC/HEVC 兼容有成熟兜底**：沿用 ffmpeg 抽封面 + 按需 GIF，避免方案 C 的前端 codec 死局。
4. **真正缺口明确且可控**：只需补两件事——(a) `find_live_photos` 扩展为**五态分类**（完整/图片缺失/视频缺失/不确定/普通照片）；(b) 预览页支持真实 `<video>` 播放（默认）并以 GIF 兜底无法解码的编码。
5. **不满足"推倒重写"动机**：方案 C 引入前端栈 + 本地服务 + codec/内存不确定性，收益不足以覆盖成本；B 已是现状，只需决定"只读 vs 复制"。

**对方案 C 的取舍**：仅当未来需要"脱离 EXE、纯浏览器跨平台分发"时才考虑，且届时仍需一个本地辅助程序处理 HEIC/HEVC——那本质上又回到"本地程序 + 网页"的混合，不如直接做 A。

## 七、风险、兼容性限制和需要补充验证的事项

### 7.1 风险与限制

- **HEIC 浏览器不可显示**【待验证具体浏览器】：现有工具靠"视频首帧 jpg"做封面，**完全没解码 HEIC**。只读预览若不生成封面，HEIC 缩略图将空白。→ 预览模式仍需 `extract_cover`（抽视频帧）或 ffmpeg 直转 HEIC→jpg。
- **HEVC(.mov) 浏览器常无法解码**【待验证】：真实 iPhone 实况 `.mov` 多为 HEVC；本样本是 `.mp4`，不能代表真实情况。→ 真实动态可能需 GIF 兜底。
- **GIF 体积膨胀**：样本 GIF 1.98 MB vs 源 mp4 468 KB（4.2×）。大量照片下存储/内存压力大 → 只读预览应默认**不生成 GIF**，仅在解码失败时按需生成。
- **`file://` 相对路径耦合**：当前 HTML 依赖 `../GIF动图/` 与 `thumb/`，单独移动会断链；只读预览若改为指向原始文件绝对路径，需验证浏览器对 `file://` 媒体的加载策略（一般 `<img>/<video>` 同源本地文件可加载，但 Canvas 跨域污染等限制需注意）【待验证】。
- **配对仅同名、覆盖式**：同名多候选会静默覆盖（行 56-60），与用户"配对不确定不允许静默合并"的要求冲突 → 必须改为"多候选→标记不确定"，不能简单取最后一个。
- **运行环境无可用 Python**（Windows 商店占位符）。开发/测试须依赖 EXE 或先修复 Python 环境；重建 EXE 需 PyInstaller 环境。

### 7.2 需补充验证（授权开发前/后）

1. 浏览器对 `IMG_0346.mp4`（H.264）与真实 iPhone `.mov/HEVC` 的实际解码结果。
2. 浏览器对 `file://` 绝对路径 `<video>/<img>` 的加载是否受限（影响"只读不复制"能否成立）。
3. 真实 HEIC 文件用 ffmpeg 直转 jpg 的成功率与速度（预览封面方案）。
4. 数千张/大视频目录下的扫描速度与内存占用基线（方案 A 流式 vs 方案 C 内存）。
5. 中文/空格/超长路径在 `os.walk` 与 ffmpeg 调用下的健壮性（代码已做 utf-8 包装，但仍需实测）。
