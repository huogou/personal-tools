# 04 · V1.3 分类体系与数据规格

> 起草：CodeBuddy（开发 AI）｜日期：2026-11-02｜状态：**V1.1 修订版**（落实评审 R-12：EXIF 排序对 HEIC 的可用性口径）
> 红线约束：本机制**不得**触碰 `.processed.json`、不得改变配对规则、不得移动/删除/改名任何原始照片（L8/L13）。

---

## 一、三层分类模型

| 层 | 名称 | 来源 | 是否落盘 | 成员判定 |
|---|---|---|---|---|
| L1 | **目录相册** | 源目录的**第一层子目录** | 仅落"相册元信息"，成员**不落盘**（运行时推导） | 该目录下的实况照片 |
| L2 | **手动相册** | 用户在客户端内新建 + 归类 | 成员落盘 | 索引 `assignments` 中显式记录 |
| L3 | **视图** | 程序内建 | 不落盘 | 「全部」「未分类」 |

**为什么分三层**：目录相册零操作、随文件夹走；手动相册跨目录、可精细组织；二者**并存且可叠加**（D2），一张照片可同时属于 1 个目录相册 + N 个手动相册。

## 二、`photo_key` 定义（索引的稳定主键）

| 项 | 规定 |
|---|---|
| 构成 | `<源根相对目录>/<基名小写>`，路径分隔符统一为 `/` |
| 例 1 | `旅行/云南/img_0346` |
| 例 2 | `img_0346`（直接位于源根） |
| 例 3 | `美食/夜市/2026-10-14/img_0346` |
| 大小写 | 基名一律小写（与现有 `.processed.json` 的 `base.lower()` 习惯一致） |
| 稳定性 | 只依赖**相对路径**，不依赖盘符/绝对路径 → 换盘符、换机器、源根改名后仍能命中（前提是相对结构未变） |
| 冲突 | 同一源根内相对路径唯一 → 天然无冲突（同名不同目录靠相对路径区分） |
| 源根变更 | 源根改变时以**相对结构**匹配；无法匹配的旧记录**保留不删**（标为"孤立记录"，UI 中不展示） |

> 与 `.processed.json` 键（`基名小写|视频目录`）**刻意不同**：后者含绝对路径，仅用于本机增量去重；前者用相对路径，用于跨机可迁移的分类索引。两者互不换算、互不影响。

## 三、`相册索引.json` 规格

### 3.1 存放位置

`输出目录/相册索引.json`（与 `.processed.json` 同级）→ 随备份产物自包含、可整目录拷贝迁移。
另提供导出/导出到任意路径（R-16）。

### 3.2 Schema

```json
{
  "schema": "livephoto-album-index/1.0",
  "updated_at": "2026-11-02T14:33:12+08:00",
  "source_root": "D:\\Photos\\iPhone",
  "albums": [
    {
      "id": "alb_dir_20261102_0001",
      "name": "旅行",
      "kind": "dir",
      "source_path": "旅行",
      "created_at": "2026-11-02T14:30:00+08:00",
      "note": ""
    },
    {
      "id": "alb_man_20261102_0002",
      "name": "家人",
      "kind": "manual",
      "created_at": "2026-11-02T14:31:20+08:00",
      "note": ""
    }
  ],
  "assignments": {
    "旅行/云南/img_0346": ["alb_man_20261102_0002"],
    "美食/夜市/img_0347": ["alb_man_20261102_0002"]
  },
  "orphans": []
}
```

### 3.3 字段表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema` | string | ✅ | 固定 `livephoto-album-index/1.0`；读到未知版本 → 拒绝写入并提示，不破坏原文件 |
| `updated_at` | string | ✅ | ISO8601 带时区，最后一次成功写入时间 |
| `source_root` | string | ✅ | 写入时的源根绝对路径（**仅供显示与迁移提示**，不参与 key 计算） |
| `albums[]` | array | ✅ | 相册清单，顺序即分类栏显示顺序（手动相册按创建时间追加在后） |
| `albums[].id` | string | ✅ | `alb_dir_<日期>_<序号>` / `alb_man_<日期>_<序号>`；**一经分配永不复用**（避免旧记录指向新相册） |
| `albums[].name` | string | ✅ | 显示名，≤30 字符 |
| `albums[].kind` | enum | ✅ | `dir` \| `manual` |
| `albums[].source_path` | string | `dir` 必填 | 相对源根的目录路径；`manual` 省略 |
| `albums[].created_at` | string | ✅ | 创建时间 |
| `albums[].note` | string | — | 备注，默认 `""` |
| `assignments` | object | ✅ | `photo_key` → **手动相册 id 数组**；空数组表示"曾归类后被移出"（保留痕迹，避免复活） |
| `orphans` | array | — | 源根变更后失配的旧 key（保留不删，UI 不展示） |

### 3.4 有效归属计算

```
有效相册(photo) = (目录相册(photo) if 第一层子目录存在 else ∅) ∪ set(assignments.get(photo_key, []))
未分类判定       = 有效相册(photo) == ∅
```

- 目录相册成员**运行时推导**，不写入 `assignments` → 索引体积与手动归类数量成正比，不随照片总数膨胀；
- 同一照片在「全部」视图中**只出现一次**（去重键 = `photo_key`）。

## 四、自动归类规则

| # | 规则 | 说明 |
|---|---|---|
| A-1 | 源根**第一层子目录名** = 目录相册名 | 「旅行/」「美食/」各成一册 |
| A-2 | 源根**直接散落**的文件 → 「未分类」 | 不自动造相册 |
| A-3 | 更深层级**不单独建相册**，但完整路径记入相册的 `source_path` 与悬停提示 | 「旅行/云南」→ 相册「旅行」，提示显示 `旅行/云南` |
| A-4 | 目录相册**首次发现时自动创建**（`kind=dir`），已存在则复用 | 分类栏顺序按发现顺序稳定 |
| A-5 | 目录在磁盘上消失 → 相册**保留**（不自动删），计数变 0 | 防误删用户的手动相册，也避免下次扫描目录顺序变化导致相册乱序 |
| A-6 | 目录改名 = 新相册 + 旧相册计数归零 | **不做自动改名跟随**（避免猜错）；提供手动「重命名相册」 |
| A-7 | 目录名含非法字符或超长 → 截断至 30 字符并加省略号，原文存 `source_path` | 保证可回溯 |

## 五、叠加、去重与排序

| # | 规则 |
|---|---|
| S-1 | 一张照片可同时属于 1 个目录相册 + 任意个手动相册（叠加生效） |
| S-2 | 「全部」视图中按 `photo_key` 去重，每张只出现一次 |
| S-3 | 相册内重复归类（同一次操作重复点击）→ 幂等，不产生重复记录 |
| S-4 | 手动相册内排序：**拍摄时间倒序**（优先读 EXIF `DateTimeOriginal`；缺失时回退文件 mtime；再缺失回退基名排序）。**EXIF 可用性边界（V1.1 修订，R-12/复核确认）**：项目仅依赖既有 Pillow（无 pillow-heif 等新依赖），**`.heic` 文件的 EXIF 读取不可用**——EXIF 优先仅对 `.mp4` / `.mov`（容器级时间元数据经 ffmpeg/文件系统可得的情形）与 Pillow 可解码的 `.jpg` 有效；`.heic` 一律走 mtime 回退，**不得为排序引入新依赖**；回退链已内建，无需用户干预 |
| S-5 | 「未分类」视图排序同 S-4 |
| S-6 | 「全部」视图排序同 S-4 |
| S-7 | 分类栏相册排序：**目录相册在前**（按发现顺序）→ **手动相册在后**（按创建时间倒序） |

## 六、写入安全、损坏恢复与迁移

### 6.1 原子写（必须）

```
1. 序列化到内存对象
2. 写 相册索引.json.tmp（utf-8, ensure_ascii=False, indent=2）
3. f.flush() + os.fsync()
4. 若已存在旧文件 → 先复制为 相册索引.json.bak
5. os.replace(tmp, 相册索引.json)      # 原子替换，Windows 亦成立
6. 失败 → 删除 .tmp，保留旧文件不变，并在日志/状态条提示
```

### 6.2 加载与自愈

| 情形 | 行为 | 用户可见提示 |
|---|---|---|
| 主文件正常 | 直接使用 | — |
| 主文件损坏、` .bak` 正常 | 用 `.bak` 恢复，并**立即**用恢复内容重写主文件 | 「分类记录已从上一份备份恢复」 |
| 主文件与 `.bak` 均损坏 | **不阻断浏览**：进入 A6 态，照片仍按目录结构展示（无手动相册） | 「相册索引读不出来，照片本身没有任何问题」+ 入口「重建分类」「先看照片」 |
| `schema` 版本未知 | 拒绝写入、保留原文件 | 「这份分类记录来自更新版本的程序，未做改动」 |
| 索引文件缺失 | 视为空索引，首次扫描后自动创建 | — |

### 6.3 重建

「从目录结构重建」= 保留所有 `kind=manual` 相册与 `assignments`，仅重建 `kind=dir` 相册集合（按当前磁盘目录重新生成）。**不删除**手动归类。

### 6.4 迁移（换机 / 换输出目录）

1. 旧输出目录 → 导出 `相册索引.json`（R-16）；
2. 新输出目录 → 导入；
3. 导入时以 `photo_key` 匹配：命中 → 生效；未命中 → 进 `orphans`（不报错、不丢失）；
4. 导入**不覆盖**已有同名索引，除非用户明确选择"合并"或"替换"。

### 6.5 与 `.processed.json` 的隔离（红线 L13）

| 项 | `.processed.json` | `相册索引.json` |
|---|---|---|
| 用途 | 增量去重（备份是否重做） | 内容分类 |
| 键 | `基名小写\|视频目录`（绝对路径） | `photo_key`（相对路径） |
| 值 | `True` / `False` | 相册 id 数组 |
| 损坏影响 | 仅影响增量（会重做一次备份，**不丢文件**） | 仅影响分类（**不丢文件**） |
| 互相影响 | **无**。分类不改变备份语义，备份不写分类 | |

## 七、分类操作与备份的关系

| 操作 | 是否触发备份 | 说明 |
|---|---|---|
| 新建/重命名/删除相册 | 否 | 只写索引 |
| 归类/移出照片 | 否 | 只写索引 |
| 扫描源目录 | 否 | 只读扫描，**不复制、不转码**（继承 V1.1 只读预览的只读原则） |
| 点击「备份」 | 是 | 走 V1.2 原备份流程，**不写分类**（除非用户显式开启"按分类同时导出"——本轮不做，S 类登记 V1.4） |

> **重要边界**：本轮分类**不改变**备份产物结构（`原始文件/`、`GIF动图/`、`网页查看器/` 保持不变），避免"分类"与"备份语义"耦合（红线 L8）。
