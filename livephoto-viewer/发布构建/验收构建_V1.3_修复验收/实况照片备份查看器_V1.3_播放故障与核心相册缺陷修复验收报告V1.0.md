## 一、原始问题与根因分析

### 1.1 问题清单与结论速览

| 编号 | 用户报告的问题 | 直接原因 | 根本原因 | 证据 |
|---|---|---|---|---|
| P1 | 点击播放后视频无法启动 | `<video>` 媒体加载被挂起：`loadstart` 后 3.3 s 抛 `stalled`，`readyState=0`、`networkState=2`、`error=null`，`play()` Promise **永不 settle** | **`album_webview.py::_run_sta` 用隐藏的 `WS_POPUP` 窗口创建 WebView2 控制器，控制器 `IsVisible=false`，Chromium 把整页判为后台页（`document.visibilityState="hidden"`）并挂起媒体子系统**；`attach()` 只显示了 Win32 窗口，从未同步 .NET 侧控制器属性 | `诊断/probe_visibility_results.json`、`诊断/probe_playback_results.json` |
| P2 | 播放中再次点击 / 重播时异常停止 | ① `stopCard()` 只做 `pause()`+`currentTime=0`，未 `removeAttribute('src')`+`load()`，解码器与缓冲未释放；② 因 P1 使 `card.state` 永久停在 `loading`，此后所有点击都被 P-10 的 `if (card.state === "loading") return;` 吞掉，表现为"点了没反应" | 播放状态机把"起播成功"完全寄托在 `play()` Promise 上，**没有超时、没有 `readyState` 判据、没有失败分类**；资源释放不完整 | `测试/smoke_playback_results.json`（修复前基线见 §六） |
| P3 | 多张照片同时播放，无单实例控制 | `playing` 变量在 `await playVideo(...)` **之后**才赋值；首张卡处于 `loading` 期间 `playing` 仍为 `null`，第二张卡可同时进入 `loading`，两个 `<video>` 并发解码 | 单实例占位与状态迁移**不是原子操作**；且 `renderGrid()` 重建 DOM、切页签、关闭窗口都没有通知前端停播与释放 | 本报告 §四（代码修复点） |
| P4 | 播放器 `readyState=0`，原有 T2 兜底未生效 | T2 由 `catch` 触发，而 `play()` Promise 永不 settle → `catch` 永不执行 | **无起播超时与失败分类**，前端无法把"挂起"识别为"失败" | `诊断/probe_playback_results.json`（`play:"pending"`） |
| R1 | 文件配对可能跨目录误配 | `album_scan.scan_source()` 的分组键是 `base.lower()`（**全库基名，不含目录**），不同子目录同名文件被合并成一组，代码只取 `[0]`，其余静默丢弃，图片与视频甚至可能来自不同目录 | 配对单元定义错误：应为 **(所在目录, 基名)** | 本报告 §四（`album_scan.py`） |
| R2 | 超过 500 张静默不显示 | `album_page.loadPhotos()` 固定 `offset=0&limit=500`，`album_api.get_state()` 还预置了 `items[:500]`；无滚动追加、无"还有更多"提示 | 前端一次性取数 + 后端预置切片，两处都截断 | 本报告 §四（`album_page.py`/`album_api.py`） |
| R3 | 仅存在视频文件就标 complete | `get_photo_detail()` **硬编码 `can_play=True`**；扫描只按"文件是否存在"判定 | 没有"文件存在 / 可读取可解帧 / 实际可播放"三层区分 | 本报告 §四（`album_api.py`/`album_media.py`） |
| R4 | 异常文件无明确分类提示 | 无法识别的扩展名静默 `continue`；缺失配对静默丢弃；损坏视频只在点击后显示统一文案 | 扫描层不产出异常统计，前端无分类文案 | 本报告 §四（`album_scan.py`/`album_page.py`） |

### 1.2 根因定位过程（全部为真实 WebView2 实测，非静态推断）

V1.3 既有的 GUI 取证（`%TEMP%\lp_v13_gui\v13_gui_results.json`）只留下现象：
`B-04 FAIL：点击后进入播放态=0（轨道='T1'，视频='rs0'）`——`readyState=0`、
`error` 为空。本轮为此新建 6 个诊断探针（`发布构建\验收构建_V1.3_修复验收\诊断\`），
逐层排除假设，**每一步结论都留有可复核的 JSON 证据**：

| 探针 | 假设 | 实测结果 | 结论 |
|---|---|---|---|
| `probe_playback.py` | 编码 / 手势 / 路径编码 / 加载策略 | `canPlayType("avc1.42E01E")="probably"`；`userActivation.isActive=true`；file:// 绝对路径、相对路径、`preload=auto`、`muted` 四种组合**全部** `events=[waiting,loadstart,stalled@3.3s]`、`readyState=0`、`error=null`、`play=pending` | **排除**编码、手势、URL 编码、加载策略 |
| `probe_fix_ab.py` | file:// 权限 / 虚拟主机名映射 | C0 基线、`--allow-file-access-from-files`、`SetVirtualHostNameToFolderMapping`、映射+file:// 混合，共 4 组**全部 NOT_PLAYABLE** | **排除**权限与虚拟主机名方案（该方案本可作为修复，但无效） |
| `probe_media_stack.py` | 子资源加载层 vs 媒体管线层 | `<img>` 加载 file:// 与虚拟 host **均成功**（960×1280）；`fetch()` 虚拟 host **成功（status 200，468660 字节）**；而 `<video>` 对 `file://` / `https://虚拟host` / `blob:` / `data:` **四种来源全部** `stalled@3.3s`、`readyState=0`、`play=pending` | **排除**资源加载层与权限；卡点在**媒体管线** |
| `probe_edge_headless.py` | 系统媒体能力是否缺失 | 独立 Edge（同一 Chromium 内核）播放**同一 file:// 视频**：`loadedmetadata@14ms → playing@179ms → readyState=4 → play=resolved → duration=2.008` | **排除**系统媒体能力缺失、文件损坏、编码不被系统支持 |
| `probe_env_ab.py` | user_data_dir 编码 / GPU / autoplay 参数 | 中文 UDD、纯 ASCII UDD、中文 UDD+`--disable-gpu`、ASCII UDD+`--disable-gpu`、中文 UDD+autoplay 参数、组合参数，共 6 组**全部 NOT_PLAYABLE** | **排除**UDD 路径编码、GPU 进程、autoplay 策略 |
| `probe_visibility.py` | 控制器/页面可见性 | 修复前：`controller.IsVisible=**false**`、`document.visibilityState=**"hidden"**` → NOT_PLAYABLE；在 WebView2 的 STA 线程内显式 `controller.IsVisible=true` + `Bounds` 后：`visibilityState="visible"` → **PLAYABLE**（`loadedmetadata@7ms → playing@100ms → readyState=4 → play=resolved → ended@2189ms`） | **根因锁定** |

**根因陈述**：`album_webview.py` 在 `_run_sta()` 中用 `CreateWindowExW(..., WS_POPUP, ...)`
创建一个**不可见**的宿主窗口，并用它调用 `CreateCoreWebView2ControllerAsync`，
WebView2 因此把控制器的 `IsVisible` 置为 `false`。随后 `attach()` 只调用
`SetParent` 与 `SetWindowPos(SWP_SHOWWINDOW)`——这二者**只影响 Win32 窗口可见性，
不会改变 .NET 侧控制器属性**。Chromium 依据 `IsVisible=false` 判定页面处于后台/隐藏状态
（`document.visibilityState="hidden"`），随即**挂起媒体子系统**：媒体请求进入
`loadstart` 后再无数据回填，3.3 s 后仅发出 `stalled`（而非 `error`），
`play()` Promise 既不 resolve 也不 reject。

这条根因同时解释了三个"看起来无关"的现象：

1. `readyState=0` 且 `error=null` —— 请求没失败，是被挂起；
2. **T2 兜底永不触发** —— T2 由 `catch` 分支进入，而 Promise 永不 settle；
3. `<img>`/`fetch` 正常、`<video>` 全来源失败 —— 图片/脚本走渲染进程主线程，
   媒体走独立的媒体管线，后台页判定只冻结后者。

> 补充实测：`document.hidden=true` 时，Chromium 不只是暂停媒体，而是让
> `play()` 的 Promise 无限期 pending，因此**任何依赖 Promise 的兜底逻辑都是死代码**。
> 这解释了为什么 V1.3 原实现"什么都没报错，却什么都不播"。

## 二、修复方案（最小范围，不换技术栈、不重写播放器）

| # | 修复点 | 文件 | 做法 |
|---|---|---|---|
| F1 | **控制器可见性同步（核心修复）** | `album_webview.py` | 新增 `sync_controller_bounds(x, y, w, h)`：把 Win32 宿主窗口的坐标/尺寸与 `IsVisible=true` **排到创建控制器的 STA 线程**执行（跨线程读写 pythonnet 的 .NET 对象会导致进程硬崩溃，故必须排队），并在 `_on_configure()` 每次布局变化时调用 |
| F2 | 控制器引用与可选配置 | `album_webview.py` | 保存 `self.controller`；新增可选 `browser_args` / `virtual_hosts`（默认空 → 行为与修复前完全一致，供诊断 A/B 复现用） |
| F3 | **退出前释放播放器** | `album_webview.py` | `stop()` 先在 STA 线程执行 `window.__lpStopAll()`（pause + 移除 src + load），再销毁窗口 |
| F4 | **播放状态机重写** | `album_page.py` | ① 起播必须有**成功判据**（`play()` resolve 且 `readyState≥2`）；② 增加 **8 s 起播超时**（覆盖 `stalled` 挂起）；③ 失败按 `decode / timeout / cancelled` 分类；④ `stopCard()` 改为完整释放（`pause` → 清事件 → `removeAttribute('src')` → `load()`）；⑤ `loading` 期间**立即占用** `playing` 槽位（单实例原子化）；⑥ `failed` 态点击 = 从头重播；⑦ 失败态不再用 `innerHTML` 覆盖卡片（否则 `<video>` 元素被销毁，重播必然失败） |
| F5 | **T2 兜底真正生效 + 异常分类** | `album_page.py` + `album_api.py` + `album_media.py` | T1 失败（超时/解码错误）→ 请求 `prepare_media`；`prepare_media` 先做**只读有效性探测**（文件存在 → ffmpeg 可读可解帧），再决定转码；失败返回 `video_missing / video_unreadable / decode_failed / transcode_failed` 等明确错误码 |
| F6 | **T3 GIF 不冒充播放成功** | `album_page.py` | GIF 兜底不再进入 `playing` 态，角标改为「动画版本（非实况视频）」，状态条明示"这不是实况视频播放"；验收中**不计入**实况播放成功 |
| F7 | **桥接调用超时** | `album_page.py` | `api()` 增加 45 s 超时并清理 pending，避免 Python 侧卡住导致前端永久等待 |
| F8 | **单实例与全局停播** | `album_page.py` + `album_host.py` + `LivePhoto_Backup.pyw` | 前端新增 `stopAll()` 与 `window.__lpStopAll`；网格重建前、切分类前、切回备份页、关闭窗口均调用；重建网格时先释放全部 `<video>` |
| F9 | **分页加载（>500 张）** | `album_page.py` + `album_api.py` | 前端改为 200 张/页、滚动到底自动追加；`get_state` 不再预置 500 条切片；状态条常驻显示「共 N 张 · 已加载 M 张 · 向下滚动加载更多」 |
| F10 | **按目录配对** | `album_scan.py` | 配对单元改为 **(所在目录, 基名小写)**；同目录多候选计入「待确认」；新增 issues 统计（`complete/photo_only/video_only/uncertain/unknown`） |
| F11 | **异常分类与提示** | `album_scan.py` + `album_page.py` | 未识别扩展名不再静默跳过，计入 `unknown`；缺失配对计入 `photo_only/video_only`；状态条以警示色展示「未完成配对/未识别」明细；视频缺失的卡片打「视频缺失」角标 |
| F12 | **视频有效性三层分离** | `album_api.py` + `album_media.py` | `_item_payload` 只声明 `media_state="exists"/"missing"`；`get_photo_detail` 删除硬编码 `can_play=True`，改为返回 `probe`（存在/可读/可解帧）+ `playable=None`（**实际可播放只能由浏览器 `playing` 事件确认，Python 侧不宣称**）；新增 `album_media.probe_video()` 只读探测（按 path+mtime+size 缓存） |
| F13 | **扫描异常透传** | `album_api.py` | `scan_source(..., issues=...)` 收集分类计数，随 `get_state`/`list_photos` 下发；扫描完成推送 `force_reload` 触发前端整页重取 |

**未做（明确不做）**：不更换 WebView2/前端技术栈、不引入 HTTP 端口服务（红线 L11）、
不改写播放器架构、不引入新第三方依赖、不改 V1.2 的 12 个受保护函数、
不动 `dist\` 与 `发布构建\验收构建_V1.2\`、不开发 iPhone 导入/Android/MTP 等未立项功能。
