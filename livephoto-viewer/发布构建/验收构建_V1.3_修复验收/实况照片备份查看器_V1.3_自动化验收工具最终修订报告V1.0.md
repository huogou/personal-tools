## 三、本轮修订内容

### 3.1 状态体系（新增 BLOCKED / NOT_RUN）

| 状态 | 含义 | 判定归属 |
|---|---|---|
| `PASS` | 实测满足预期 | 产品通过 |
| `FAIL` | 实测不满足预期，且能归因于产品 | 产品失败 |
| `BLOCKED` | 工具/环境缺陷导致无法得出有效结论 | **不算产品失败，也不算通过** |
| `UNVERIFIED` | 已执行但无法判定 | 中性 |
| `NOT_RUN` | 未执行 | 中性 |

`BLOCKED` 附带 `blocked_by`：`tool_or_env` / `tool_exception` / `timeout`。

**已接入 BLOCKED 的场景**（共 12 处）：

| 测试项 | 触发 BLOCKED 的条件 |
|---|---|
| T-01 | 通信探针 `1+1` 失败（`evaluate_sync` 超时/页面无响应） |
| T-02 | 步骤开始或结束时通信探针失败 |
| T-03 | 任一目标卡片 `index_of` 未命中 |
| T-04 | 三张目标卡片任一未命中 |
| T-05 | 首张卡片未命中 |
| T-06 | 滚动加载完成后损坏样本卡片仍未命中 |
| T-09 | 长路径卡片未命中 |
| T-11 | 注入后卡片未命中 |
| 任一步骤 | 脚本自身抛异常（`tool_exception`）；全局 25 分钟超时（`timeout`） |

### 3.2 12 项必有独立记录

- 脚本内置 `PLAN`（T-00…T-11）；
- `_flush()` 每次输出都会遍历 `PLAN`，未执行项自动补 `NOT_RUN`；
- `finish()` 输出同样保证 12 项齐全；
- 因此**即使进程在中途终止，JSON 仍是 12 项完整列表**（已执行项 + 未执行项）。

### 3.3 坐标定位修复

| 旧实现 | 新实现 |
|---|---|
| `GetWindowRect().top + getBoundingClientRect().y` | `ClientToScreen(WebView2 子窗口, 0, 0)` 得到视口原点，再加 `getBoundingClientRect()` 坐标 × `devicePixelRatio` |
| 未记录落点是否有效 | 记录客户区原点、卡片尺寸、是否在屏幕内 |
| 未先激活窗口 | 点击前 `ShowWindow(SW_SHOW)` + `SetForegroundWindow` + 0.45 s 等待 |

> 旧实现漏了标题栏高度（约 31 px），点击必然偏下；这是历史 T-01 物理点击落空的直接原因。

### 3.4 稳定样本定位

| 问题 | 修复 |
|---|---|
| 损坏样本 `BROKEN.mp4` mtime 最新，排序占据 `items[0]` | 语料改放 `Z_异常/`，并把 `BROKEN.HEIC` 改为 `copy2` 后与 `BROKEN.mp4` 一起 `utime` 到 30 天前 |
| `index_of` 失败时静默 `idx = 0` | **删除回退**，一律记 `BLOCKED` 并跳过 |
| T-03/T-04/T-05 用固定索引 | 全部改为按 `photo_key` 定位 |
| 无法确认排序是否稳定 | T-00 新增断言：第 0 张不得是 `Z_异常/broken` |

> `BROKEN.HEIC` 用 `copy2` 而非硬链接，避免 `utime` 改到 `测试样本\IMG_0346.HEIC` 本体（样本保护）。

### 3.5 超时处理

| 层 | 处理 |
|---|---|
| 产品侧 | 播放起播 8 s 超时（上一轮已实现） |
| 工具侧 | `evaluate_sync` 20 s；卡片等待 4–12 s；T-06 分页加载 70 s；T-08 90 s |
| 全局 | 25 分钟 watchdog：超时后把未执行项记 `BLOCKED(timeout)` 并强制 `finish()` |
| 结论归属 | 工具侧超时 → `BLOCKED`，不记产品 `FAIL` |

### 3.6 即时落盘与异常退出

| 机制 | 实现 |
|---|---|
| 即时落盘 | `record()` / `unverified()` 每次调用 `_flush()` 写 `acceptance_results.json`（`partial=true`） |
| 退出兜底 | `atexit` 注册 `_on_exit()`：未完成时再写一次并记录 `[ATEXIT]` |
| 未捕获异常 | `sys.excepthook` 记录 `[EXCEPTHOOK]` 并落盘 |
| native 崩溃 | `faulthandler.enable(证据\faulthandler.log)` |
| 运行日志 | 每行同时写 `证据\acceptance_run_<时间戳>.log`（实时） |
| 步骤追踪 | 每步打印 `[STEP] t0x（剩余 N 步）`；异常打印完整 `[TRACEBACK]` |

### 3.7 假绿自检

`self_check()` 写入结果 JSON 的 `self_check` 字段：

| 检查 | 内容 |
|---|---|
| `sample_unchanged` | 语料构造前后对 `测试样本\IMG_0346.HEIC/.mp4` 计算 SHA256 并比对 |
| `plan_total` | 固定 12 |
| `status_all_legal` | 所有状态必须在 5 种合法值内 |
| `record_overrides` | 同一项状态被改判时留痕（正常应为空） |
| `has_skip_mechanism` | 固定 `false`（脚本无 SKIP） |

## 四、T-03 异常中止原因调查

### 4.1 证据清单

| 证据 | 内容 |
|---|---|
| `测试\acceptance_run2_stdout.txt` | 最后一行是 T-02 的 `[FAIL]`，之后无任何输出 |
| `测试\acceptance_run2_stderr.txt` | 仅一条与业务无关的 `UnicodeDecodeError`（subprocess reader 线程，GBK 解码），**无 Python traceback** |
| `测试\acceptance_run3_stdout/stderr` | 与 Run 2 完全一致 |
| `测试\acceptance_run4_stdout.txt` | `T-00 PASS` → `T-01 FAIL`（`捕获瞬间={}`、`state=None`）→ 无后续 |
| `测试\acceptance_run4_stderr.txt` | **0 字节** |
| `证据\faulthandler.log`（Run 4） | **0 字节**（无 native 崩溃栈） |
| 负责人截图（Run 4） | 窗口标题变为「实况照片备份查看器 V1.3（未响应）」+「Python 未响应」系统对话框 |
| 代码结构 | 所有 `step_*` 在 **Tk 主线程**执行；`wait_card` 用 `time.sleep` 轮询 + `evaluate_sync` 内部 `done.wait(20)` 阻塞等待 |

### 4.2 分析

1. **排除"Python 未捕获异常"**：三次运行 stderr 都没有 traceback；若有异常，`pump()` 的 try/except 会捕获并记录，不会静默消失。
2. **排除"native 崩溃"（Run 4）**：`faulthandler.log` 为 0 字节；但 Run 2/3 当时**未启用** faulthandler，**不能完全排除**。
3. **最可能原因**：主线程被阻塞式轮询长期占用（单次最多 20 s，多次叠加），Windows 判定窗口"未响应"；随后进程被系统或人工结束。Run 4 的截图与 `evaluate_sync` 返回 `None` 均指向这一点。
4. **为什么 Run 2/3 连"未响应"提示都没留下**：进程在无交互情况下被结束（可能由系统或上一次操作的清理动作终止），未走 `finish()`，因此没有 JSON。

### 4.3 结论（如实）

> **无法 100% 确认** T-03 阶段进程终止的唯一原因：缺少该时刻的 native 崩溃栈与 Python traceback。
> 现有证据**支持**"主线程阻塞 → 窗口未响应 → 进程被结束"这一解释，**不支持**"产品播放功能崩溃"这一解释。
> 因此历史 T-01/T-02 的 `FAIL` 在性质上更可能是 **BLOCKED（工具缺陷）**；本轮已把同类场景改为记 `BLOCKED`，
> **但历史记录按原样保留为 FAIL，不改写、不删除。**

### 4.4 本轮已采取的对应措施

| 措施 | 目的 |
|---|---|
| 通信探针 `1+1` | 明确区分"产品不播"与"页面无响应" |
| 全局 25 分钟 watchdog | 避免无限期阻塞 |
| 增量落盘 + atexit + excepthook + faulthandler | 即使再次异常终止，也能定位到具体步骤并保留已完成结果 |
| 状态体系引入 `BLOCKED` | 工具缺陷不再被误记为产品 FAIL |

> **注意**：上述措施**尚未执行验证**（本轮按要求不启动程序）。主线程阻塞式轮询的结构本身**未改动**——若要根治"窗口未响应"，需把驱动改为完全非阻塞（`root.after` 链式回调 + 异步等待），这属于下一轮工具改造，需产品确认是否值得投入。
