附件 04｜方向三 Android MTP 导出 + 方向四 完整流程逐环节风险表
一手依据：Microsoft WPD 文档（附件 01 C1–C8）、Android MediaStore 文档（A5/A6）、Apple 导入文档（B2/B3/B4）

════════ 一、方向三：Android 手机直接连接 Windows 导出 ════════
Q1 Windows 能否识别 Android USB 设备？
【A · 官方依据】WPD 驱动概览：Windows 内置类驱动支持 MTP / PTP / MSC over USB（C1）；设备管理器中常显示为「便携设备」。
【C】用户须在手机端选择「文件传输 / MTP」模式并解锁；部分品牌需 OEM USB 驱动（Microsoft Q&A C10 为社区级证据，非规范）。
【E】企业环境可能被组策略 `WPDDevices_DenyWriteAccess*` 禁止写入（C7）。

Q2 MTP 协议能否用于照片和视频导出？
【A · 官方依据】WPD 提供 `IPortableDeviceContent::CreateObjectWithPropertiesAndData`，以「属性集合 + IStream 数据流」在设备上创建对象（C4）；官方示例 C5 给出完整流程：取必需属性（父对象 ID、流字节数、文件名、无扩展名名称、内容类型、内容格式）→ CreateObjectWithPropertiesAndData → StreamCopy → `Commit` → `GetObjectID`。
【官方依据·原子性】原文："The object will not be created on the device until the application sends the data by calling ppData->Commit. To abandon a data transfer in progress, you can call ppData->Revert."
【观点】该语义适合做「写完才可见」的原子导出，可与项目现有「逐条落盘 + 安全取消」模式对齐。

Q3 能否将转换后的 Motion Photo 直接写入手机？
【B + C · 技术上可行，尚未实测】WPD 是 COM API，Python 需 pywin32 / comtypes 等社区绑定（Microsoft 无官方 Python SDK）；写入的是「新对象」而非文件路径。
【E · 官方依据】KB2736948（C8）明确："Windows.Storage.Streams.DataWriter will fail if the device is an MTP 1.0 device or MTP 2.0 device that does not support streams because neither support writing to an existing file on the device... most MTP devices currently in the market are still MTP 1.0 devices."
  → **只能新建，不能覆盖/追加已有文件**；想更新同名文件须先删除再新建，风险上升。
【E · 官方依据】C8 另记载 MTP 2.0 上更新文件后 `StorageFile` 可能返回 stale size，需重新获取对象。
【需要真实设备验证】写入后是否自动进入 MediaStore 索引、是否被标记为 `SPECIAL_FORMAT_MOTION_PHOTO`、XMP 是否被系统保留、相册 App 是否立即可见。
【观点】MTP 单文件可能达数 MB～数十 MB（主图 + 视频），中断概率随体积上升；必须设计「临时名 → 校验 → 提交 → 确认」流程，但 MTP 对象模型未必支持重命名【暂时无法确认】。

Q4 能否自动识别目标设备的照片目录？
【E · 官方依据】Android 官方没有「MTP 端统一照片目录」规范。`MediaStore.MediaColumns.RELATIVE_PATH`（API 29+，A5）规定相对路径仅用于组织目的，原文明确 "you should not attempt to construct or access a raw filesystem path using this value"；insert 时若置 NULL，由系统按 MIME 放到相关默认位置（image/jpeg → `Environment.DIRECTORY_PICTURES`）。
【C · 官方依据】WPD 提供 `WPD_COMMAND_DEVICE_HINTS_GET_CONTENT_LOCATION`：「Retrieves the object IDs of folders that can hold an object of a specified type」（C6）→ 正确做法是查询设备提示，而非硬编码 `DCIM/Camera`。
【暂时无法确认】各品牌 MTP 暴露的存储对象树、`DCIM/Camera` 是否存在、是否允许在该位置新建对象；Microsoft Q&A（C10）提到 Pixel 的 `DCIM/Camera`，属社区线索**不作品牌结论**。
【观点】推荐交互：列出设备返回的可写位置让用户确认一次并记住，而不是自动猜测目录。

Q5 不同品牌的目录和权限差异？
【暂时无法确认】本轮未找到任何官方品牌差异对照表，**不虚构** Samsung / 小米 / OPPO / vivo / 华为 / Pixel 的目录、权限或播放行为。
【官方依据·可确认部分】Android 10（API 29）起应用侧写入共享媒体走 MediaStore，且 `RELATIVE_PATH` 内容须放在与媒体类型匹配的顶层目录下（A5）；但这是 App 侧约束，MTP 是系统级通道，二者不等价。
【需要真实设备验证】见附件 06 矩阵。

Q6 是否需要额外驱动或第三方依赖？
【C】WPD = Win32 COM，Python 侧需 pywin32 / comtypes（社区绑定，无官方 Python SDK）；Android 端多数免驱（MTP 类驱动），个别品牌需 OEM USB 驱动。
【零依赖退路 · 技术上可行】不做 MTP 写入：工具只把 Motion Photo 输出到本地文件夹，由用户自行用 Windows 资源管理器拖入手机。此路径零新增依赖、零驱动、风险最低，但多一步人工操作。
【观点】若 D2 裁定「不碰设备层」，Q6 整项可消失，是成本最优解。

════════ 二、方向四：完整流程逐环节风险表 ════════
流程：① iPhone 拍摄 → ② USB 连 Windows → ③ 导入实况照片 → ④ 本地相册浏览 → ⑤ 保存到移动硬盘 → ⑥ 转换为 Android Motion Photo → ⑦ USB 导出到 Android → ⑧ 手机相册播放
评级：障碍 = 技术障碍（官方依据/待验证）｜成本 = 用户操作成本（观点）｜风险 = 数据丢失风险（观点，基于上游 V1.0 与官方限制推导）

环 环节                  技术障碍                                       用户成本  数据丢失风险
① iPhone 拍摄            无（用户既有行为）；但相机「高效/兼容性最佳」决定后续格式【B2/B3】  低      低；若改「兼容性最佳」，此后不再产生 HEIC/HEVC 原片（不可逆的拍摄设置变化）
② USB 连 Windows        需 Apple 设备 App、解锁、点「信任」【B2/B5 = C】         中      低；未授权时导入无法开始，无写入即无损失
③ 导入实况照片           HEIF/HEVC 可能转 JPEG/H.264【B3】；iCloud 优化存储须先下载原片【B2/B4】；Content Identifier 是否保留未知【D】  中-高  **高**：静默转码不易察觉，可能把「低分辨率/已转码」当作原片长期保存
④ 本地相册浏览           上游 V1.0：V1.2 已发布；V1.3 相册页未验收、播放 3 FAIL、>500 张取不到  中      低（只读）；但「以为已能播放」会误导后续判断
⑤ 保存移动硬盘           纯本地文件复制，无技术障碍；但 `相册索引.json` 存 source_root 绝对路径，换盘符/断开重开行为未验证【上游 V1.0 3.4/R14】  低      中：路径失效可能让相册索引找不到源文件
⑥ 转换 Motion Photo     须按官方 1.0 重建 XMP 与容器；HEIC 版需 mpvd box【A1】；HEVC 兼容性未知【D】  中      **高**：单文件拼接若长度/XMP 错误会产出「看似成功实际不可播」的文件；必须保留原始双文件
⑦ USB 导出 Android      WPD 可新建对象但 MTP 1.0 不能写已有文件【C4/C8】；目录无统一规范【A5/C6】；写入后索引行为未知【D】  中-高  **高**：传输中断可能产生半成品对象；无回滚手段
⑧ 手机相册播放           仅 Android 框架层有支持证据【A2/A4/A6】；品牌相册 App 兼容【暂时无法确认】  低      **高**：若未验证即删除电脑/手机原文件，动态内容可能永久丢失

跨环节结论
· 【技术上可行，尚未实测】每一环单独都有可行路径；**无任何官方文件保证端到端互通**。
· 【需要真实设备验证】至少 4 环：③（导出保真）、⑥（HEVC 兼容）、⑦（MTP 写入与索引）、⑧（相册播放）。
· 【已有官方依据】至少 2 环需联网或外部组件：②（Apple 设备 App 从 Microsoft Store 安装）、③（iCloud 优化存储下载全分辨率原片需联网 + Apple ID）。
· 【观点】用户操作成本 ≥ 5 次人工介入（装 App/解锁信任/选 USB 模式/选目录/转换等待/导出后验证），与「每年备份一次」的低频场景叠加，易用性风险高。
· 【观点·红线】在 ⑧ 验证通过前，不得删除任何一端原始文件；项目现有「只复制不删除源文件」的约束（上游 V1.0 附件 03）必须延续。
· 【不建议实施】把「iPhone → Android 一键转换」作为首版目标：链条最长、不可验证环节最多、失败后定位困难。
