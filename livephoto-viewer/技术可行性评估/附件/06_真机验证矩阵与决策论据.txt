附件 06｜真实设备验证矩阵 · 开发难度与优先级 · 不建议方案正反论据
声明：本附件含【观点】与建议，不构成开发授权；技术选型与优先级由 ChatGPT 裁定。

════════ 一、真实设备验证需求（对应主报告 3.7）════════
V 组：iPhone 导入侧
V-1 设备：至少 1 台 2020 年后的 iPhone（能拍 HEVC 实况）+ Windows 10/11；须分别测「相机=高效」与「相机=兼容性最佳」两态。
V-2 iCloud 两态：关闭 iCloud 照片 / 开启且「优化 iPhone 储存空间」，对比 USB 导入结果。
V-3 逐项检查：① 主图与影片是否成对导出 ② 扩展名与命名规则（.HEIC/.JPG、.MOV/.MP4）③ 分辨率/编码是否被转码（对照 B3）④ 全分辨率是否保住（对照 B2/B4）⑤ QuickTime Content Identifier 与 MakerNote 是否仍存在、能否用于配对 ⑥ 拍摄时间/GPS 等 EXIF 是否保留 ⑦ 未点「信任」/拔线/中断时的实际行为。
V-4 须补齐上游 V1.0 已登记的缺口：真实 iPhone HEVC .mov 样本（当前 `测试样本\` 只有 H.264 .mp4，见上游附件 04）。

A 组：Android 侧
A-1 设备矩阵【建议，非结论】：至少 2 个品牌 × 2 个 Android 版本（含 1 台 Android 14+ 与 1 台较旧版本）；每台用其**默认相册 App** 验证，不只用 ExoPlayer Demo。
A-2 格式矩阵：Motion Photo 1.0 JPEG 版 / HEIC 版；视频容器 video/mp4 与 video/quicktime；编码 H.264 与 HEVC（若有真实样本）。
A-3 逐项检查：① 相册是否识别为动态照片 ② 能否播放视频与音频 ③ 静帧与视频切换是否符合 `MotionPhotoPresentationTimestampUs` ④ 文件重命名/复制后是否仍识别 ⑤ MediaStore 是否标记 `SPECIAL_FORMAT_MOTION_PHOTO` ⑥ 拍摄时间是否正确显示。
A-4 MTP 写入：WPD 枚举 → 查询 `WPD_COMMAND_DEVICE_HINTS_GET_CONTENT_LOCATION` → 新建对象 → Commit → 断电/拔线中断 → 检查媒体库是否出现半成品、能否删除、是否需重启才可见。
A-5 明确禁止：在 V 组与 A 组完成前，不得对外使用「支持 iPhone 直连导入」「支持 Android 动态照片」「兼容某品牌」等表述。

W 组：Windows / 打包侧
W-1 WPD COM 在 Python（pywin32/comtypes）下的枚举与写入可行性、STA/线程要求。
W-2 MTP 1.0 与 2.0 行为差异（KB2736948）、组策略禁止写入的表现。
W-3 新增依赖在 PyInstaller 单文件下的可打包性、体积增量实测、`ffmpeg -L` 实际许可证输出。

════════ 二、预计开发难度（【观点】定性排序，非工期估算）════════
难度  事项                                              主要依据
低    本地「普通照片 + 视频」备用导出、保留原始双文件      纯文件复制，项目已有 copy2 / 安全取消模式
中    Motion Photo 1.0 JPEG 版生成 + 独立规范校验器        XMP packet 构造、字节追加、Item:Length 求和、命名正则；可纯离线单测
高    Motion Photo 1.0 HEIC 版                        mpvd box、HEIF 内 XMP box、Padding=8、HEIF 编码栈与 GPL wheel
高    WPD COM 设备写入（含中断原子性、目录查询、降级）     COM/apartment、MTP 只能新建、无统一目录、索引行为未知
很高  iOS 设备层直连（识别/授权/文件访问/异常恢复）        Apple 组件前置、iOS 17+ tunnel、信任流程、GPL 库、版本漂移
最高  完整 8 环链路串通 + 双端真机验收                   4 环待验证、2 环需联网/外部组件、失败定位困难
【观点】难度排序不等同于优先级：难度最低的「备用导出」恰好也是数据安全性最高的一项。

════════ 三、建议开发优先级（【观点】排序建议，交 ChatGPT 裁定；★ 不构成开发授权）════════
P0 先决条件（非开发）：补真实 iPhone HEVC .mov 样本；裁定产品定位 D1；清点并处理现有 GPL 合规；先解上游 V1.0 的 D1/D2 与 R1（V1.3 播放 3 FAIL）。
P1 本地「保留原始双文件 + 普通照片/视频备用导出」：不碰设备层、零新增驱动、可逆、可直接验收。
P2 Motion Photo 1.0 JPEG 版 + 独立规范一致性校验器；真机播放验收作为独立闸门（阶段 A / 阶段 B 分开）。
P3 Android MTP 写入：需 A 组设备矩阵支持，且须先解决「只能新建」与目录不确定性。
P4 iPhone USB 直连：成本、许可证、维护三项最高，建议最后评估或明确不做。
【观点】若 D2 裁定「只处理本地文件」，P3/P4 可整体移除，方案收敛为 P1+P2，复杂度显著下降。

════════ 四、不建议实施的方案 · 正反双方论据 ════════
N1 用 pymobiledevice3 / libimobiledevice 直读 iPhone 照片库（替代 Windows 现有导入）
  支持方：① 纯 Python、跨平台，提供 usbmux 枚举与 AFC 文件访问，理论上可绕过 Windows 照片 App 的转码行为；② 若能读到原始文件，更可能保留 Content Identifier，从而支持基于元数据的配对；③ 有活跃维护与文档。
  反对方：① GPL-3.0（闭源/对外分发前需合规评估）；② Windows 需 iTunes 或 usbmuxd 前置，iOS 17+ 还需 CoreDevice/RemoteXPC tunnel，17.0–17.3.1 在 Windows 上需额外驱动且项目不提供；③ libimobiledevice 自述未获 Apple 授权/认可，随 iOS 版本漂移风险高；④ 设备解锁与「信任」仍不可省，用户体验并未简化；⑤ 与「免费依赖、免安装、低维护、纯本地」目标冲突。
  裁定【不建议实施】（至少在「自用 + 低维护」定位下）。若 D1 改为对外产品且接受 GPL 与长期维护，可重评，但须先做 W-1/W-3 实测。

N2 按旧 Microvideo V1（`GCamera:MicroVideoOffset`）生成 Motion Photo
  支持方：中文资料多、实现最简单、只需写几个 XMP 字段 + 追加视频。
  反对方：Android 官方 Motion Photo format 1.0 明确「These properties ... are deleted in this specification and must be ignored if present」，偏移已由 Container/Item 的 Item:Length 取代；按旧规范产出的是历史格式，现代读者可能忽略其视频。
  裁定【不建议实施】。

N3 首版即做 HEIC 主图的 Motion Photo
  支持方：贴近 iPhone 原始格式、官方规范明确允许 image/heic、ExoPlayer 标 HEIC Motion Photo = YES。
  反对方：① 必须构造顶层 mpvd box、Item:Padding=8、HEIF 内 XMP box，现有 Pillow/imageio-ffmpeg 栈不具备；② 引入 pillow-heif 预编译 wheel 会带 x265(GPL-2.0)/libheif(LGPL-3.0)，合规与体积双升；③ 各品牌相册 App 对 HEIC Motion Photo 的识别率【暂时无法确认】；④ 上游 V1.3 连基础视频播放尚有 3 FAIL，叠加容器复杂度风险过高。
  裁定【不建议实施（首版）】；建议 JPEG 版验证通过后再评估。

N4 覆盖/追加写入手机已有文件，或转换成功后自动删除原始文件
  支持方：流程短、无需用户清理、看起来「一步到位」。
  反对方：① KB2736948 明示 MTP 1.0 及不支持 streams 的 MTP 2.0 不能写入已存在文件；② MTP 对象模型缺少可靠的原子替换/回滚；③ 手机相册播放尚未验证前删除原件，动态内容可能不可逆丢失；④ 与项目现有「只复制、不删除源文件」红线冲突。
  裁定【不建议实施】。

N5 用 iCloud / 云端中转取全分辨率原片
  支持方：Apple 官方说明 iCloud 照片始终存原始全分辨率，可解决优化存储下 USB 拿不到原片的问题。
  反对方：① 需联网 + Apple ID + 可能占用 iCloud 空间；② 与 README「零第三方服务、零联网、纯本地」及个人开发者无服务器定位冲突；③ 引入账号、隐私与数据出境等新问题，需独立隐私说明（项目目前没有）。
  裁定【不建议实施（维持纯本地定位时）】；若 D1 改为对外发布并可接受联网，可重评但须单独立项。
