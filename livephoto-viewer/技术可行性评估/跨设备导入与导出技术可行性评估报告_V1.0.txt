§0 前提复述与质疑（先纠错，再评估）
复述：不以现有功能可靠为前提，评估「iPhone USB 导入 / Motion Photo 转换 / Android MTP 导出 / 全链路」四方向的未来扩展能力，只交结论不授权开发。
质疑 1【观点】「跨设备导入导出是既定下一步」是产品方向假设，不是事实：V1.0 报告待裁定 D1–D10 未含此项，属范围扩张，需 ChatGPT/彦祖立项裁定。
质疑 2【事实纠正】任务书问「XMP 元数据及视频偏移信息的要求」，但 Android 官方 Motion Photo format 1.0 已明确删除 `MicroVideoOffset`（旧 Microvideo V1 属性，若存在必须忽略），改由 Container/Item XMP 的 `Item:Length` 定位。按旧资料实现会产出非标准文件。
质疑 3【事实纠正】「HEIC 作为动态照片载体存在兼容性限制」需修正：官方 1.0 规范明确允许 `image/heic` 与 `.HEIC` 文件名，限制在实现复杂度（须写 `mpvd` box、Padding=8），不是规范禁止。
质疑 4【事实】「保留原始 HEIC/MOV」与 Apple 官方给出的 Windows 兼容建议直接冲突（见 3.2），不是纯工程问题。

① 一页结论（5 条）
1【已有官方依据】两条链路的底层机制都存在：Windows WPD 类驱动原生支持 PTP/MTP/MSC；Android 官方发布 Motion Photo format 1.0 单文件规范；Apple 官方定义 Live Photo 的 Content Identifier 关联。但「机制存在」≠「本项目已支持」。
2【不建议实施】iPhone 设备层直连（pymobiledevice3 等）成本最高：需 iTunes/usbmuxd 或 Apple 设备 App、iOS 17+ tunnel、设备信任授权，且 pymobiledevice3 为 GPL-3.0。更稳的路径是「用 Windows 现有导入得到本地文件，Python 只处理本地目录」。
3【已有官方依据】Apple 明确：USB 导入 PC 时 HEIF/HEVC 可能被转为 JPEG/H.264（需开「保留原片」）；iCloud 优化存储开启时须先把全分辨率原件下载回设备再导入。故「原样保留 + 纯本地零联网」在部分真实场景下不可兼得。
4【已有官方依据】Motion Photo 1.0 允许 `video/quicktime`（MOV）容器，规范层面不强制重编码；是否需转 H.264 取决于目标 Android 设备解码能力【需要真实设备验证】。生成文件成功 ≠ 手机相册播放成功。
5【已有官方依据 + 项目自述】许可证是比技术更前置的阻断项：现有 EXE 已打包 imageio-ffmpeg 的 GPL 构建 ffmpeg；项目 V1.2/V1.3 均无许可证清单。若产品定位从「自用」改为「对外分发」，须先做合规。

③ 已核实事实
3.1 方向一｜iPhone USB 直接导入 Windows（A–E 分类，逐问 8 条见附件 02）
  Windows 能否识别【A+C】WPD 类驱动原生支持 PTP/MTP/MSC over USB；但 iPhone 侧需从 Microsoft Store 装「Apple 设备」App（提供设备服务/驱动），并需解锁 + 点「信任此电脑」
  驱动组件【C】Apple 设备 App / Apple Mobile Device Service（旧称 iTunes 组件）；Python 库 pymobiledevice3 在 Windows 需 iTunes 或 usbmuxd 前置，iOS 17+ 需 CoreDevice/RemoteXPC tunnel，17.0–17.3.1 还需其不提供的额外驱动
  Python 设备识别与媒体访问【B+C】无官方 Python iOS SDK；两条路：① WPD COM（IPortableDeviceManager.GetDevices / IPortableDevice.Open），需 pywin32/comtypes 等社区 COM 绑定；② pymobiledevice3（纯 Python，GPL-3.0，含 AFC 文件访问）。均为【C】
  能否读照片及配套视频【A+E】Windows 照片 App / 资源管理器从 DCIM 导入可得到成对图+视频（项目 V1.2 样本即来自此类流程），但 Apple 官方未承诺 Live Photo 双文件必然成对导出
  能否识别关联信息【已有官方依据 + D】Apple 官方：Live Photo 影片恒含 `AVMetadataQuickTimeMetadataKeyContentIdentifier`，与静态图 `kCGImagePropertyExifMakerNote` 中的对应标识关联 → 机制确存在；但 USB/PTP 导出后该元数据是否保留，官方无说明【需要真实设备验证】
  保留原始 HEIC/JPEG、MOV、拍摄时间【已有官方依据 + E】Apple 116944：USB 导入 PC 时 HEIF/HEVC「可能转换为 JPEG 或 H.264」，需在 iPhone「设置→App→照片→保留原片」；120267 又建议用「兼容性最佳」（此后以 JPEG/H.264 拍摄）→ 两条官方口径相互制约
  iCloud 优化存储【已有官方依据】120267：开启 iCloud 照片时「必须先将照片原始的全分辨率版本下载到 iPhone/iPad，然后再导入到 PC」；105061：优化存储时全分辨率存于 iCloud、设备留节省空间版本 → USB 直导可能拿到低分辨率，补下载需联网
  未授权/断开/中断【技术上可行，尚未实测】设备枚举失败、未点信任、拔线、传输中断可在应用层设计为「失败即停 + 原子落盘 + 逐条校验 + 可续传」（项目 V1.2 已有安全取消/逐条落盘可复用），但无 Apple 官方 iOS 侧 API 保证，需真机验证
3.2 方向二｜Android Motion Photo 转换与导出（规范细节见附件 03）
  结构区别【已有官方依据】Apple = 双文件（主图 + MOV，Content Identifier 关联）；Motion Photo 1.0 = 单文件：主图 JPEG/HEIC/AVIF + 追加视频，靠 Camera XMP + Container XMP 目录定位
  官方 1.0 规范【已有官方依据】文件名须匹配 `^([^\s/\\][^/\\]*MP)\.(JPG|jpg|JPEG|jpeg|HEIC|heic|AVIF|avif)`；`Camera:MotionPhoto`=1、`Camera:MotionPhotoVersion`=1、`Camera:MotionPhotoPresentationTimestampUs`；Container 命名空间 `http://ns.google.com/photos/1.0/container/`、Item 命名空间 `.../container/item/`，`Item:Mime`、`Item:Semantic`(Primary/MotionPhoto/GainMap)、`Item:Length`（次要项必填，字节长度）、`Item:Padding`
  ★ 关键版本差异【已有官方依据】`Camera:MicroVideo`/`MicroVideoVersion`/`MicroVideoOffset`/`MicroVideoPresentationTimestampUs` 属旧 Microvideo V1，本规范「已删除，若存在必须忽略」；`MicroVideoOffset` 由 Container/Item 的 `Item:Length` 取代。按旧资料实现 = 产出非标准 1.0
  HEIC 载体【已有官方依据】允许 `image/heic` + `.HEIC`；但 ISOBMFF 主图必须以顶层 `mpvd`（Motion Photo Video Data）box 结束，`Item:Padding` 必须等于 8（box 头长度）；视频项须位于文件末尾且其后不得有任何字节 → 需 ISOBMFF box 级写入，现有 Pillow/imageio-ffmpeg 栈不具备
  视频重编码【已有官方依据 + D】`Item:Mime` 允许 `video/mp4` 与 `video/quicktime`（MOV），规范性引用含 Apple QuickTime、HEVC、AVC、MP4/ISOBMFF → 规范不强制重编码，iPhone .mov 理论上可原样追加；但 HEVC 在目标 Android 端能否直解【需要真实设备验证】，不兼容时才需转 H.264（现有 ffmpeg 栈可覆盖）
  拍摄时间与元数据【技术上可行，尚未实测】EXIF DateTimeOriginal 可留在主图 XMP/APP1；规范用 `Camera:MotionPhotoPresentationTimestampUs` 表达静帧对应视频时刻；MP4 `mvhd` creation_time 可保留。跨格式迁移后字段一致性无保证
  品牌/相册 App 兼容性【暂时无法确认】官方只证明框架层：Media3 ExoPlayer 支持 JPEG Motion Photo 与 HEIC Motion Photo、MediaStore 有 `SPECIAL_FORMAT_MOTION_PHOTO`、API 33 Photo Picker 有 `STANDARD_MIME_TYPE_EXTENSION_MOTION_PHOTO`。**不虚构任何 Samsung / 小米 / OPPO / vivo / 华为 / Pixel 相册 App 兼容结论**，须真机矩阵验证
  三项重点评估【技术上可行，尚未实测】① 生成标准 1.0 文件（JPEG 版）② 同时保留原始照片与视频独立文件 ③ 转换失败降级为「普通照片 + 视频」备用导出 —— 均可纯本地实现；但生成成功 ≠ 手机相册播放成功，二者必须分开验收
3.3 方向三｜Android USB 直接导出（详见附件 04）
  Windows 识别【A】WPD 类驱动原生支持 MTP；用户需在手机选「文件传输/MTP」并解锁；部分品牌需 OEM USB 驱动【C】
  MTP 用于照片/视频导出【A】WPD 官方 `IPortableDeviceContent::CreateObjectWithPropertiesAndData` 支持带属性+数据流创建设备对象，`Commit` 后才真正落设备
  写入转换后 Motion Photo【B+C+E】理论可行（新建对象），但 MTP 是对象模型非 POSIX 文件系统；Microsoft KB2736948 明示 MTP 1.0（及不支持 streams 的 MTP 2.0）**不能写入已存在文件/追加**，只能新建；写入后是否触发 MediaStore 索引、是否被识别为 Motion Photo【需要真实设备验证】
  自动识别目标照片目录【E】Android 官方无「MTP 端统一照片目录」规范；`MediaStore.MediaColumns.RELATIVE_PATH`(API 29+) 说明由系统按 MIME 决定默认位置（image/jpeg → DIRECTORY_PICTURES），且明确「不应据此构造原始文件路径」。DCIM/Camera 是常见约定非规范，品牌差异【暂时无法确认】
  额外依赖【C】WPD 为 COM API，Python 需 pywin32/comtypes 社区绑定；零依赖退路 = 用户自行用资源管理器拖入手机
3.4 方向四｜完整流程（9 环节逐环节表见附件 04）
  iPhone 拍摄 → USB 连 Windows → 导入 → 本地浏览 → 存移动硬盘 → 转 Motion Photo → USB 导出 Android → 相册播放
  结论【技术上可行，尚未实测】：每一环单独都有可行路径，但**无任何官方文件保证端到端互通**；至少 4 环需真机验证、2 环需联网或外部组件（Apple 设备 App 安装、iCloud 原片下载）
  数据丢失风险最高三处【观点，基于上游 V1.0 与官方限制推导】：USB 导入静默转码（原片丢失不可察觉）、MTP 写入中断产生半成品对象、用户在验证手机可播放前删除电脑/手机原文件
  用户操作成本【观点】：设备解锁+信任、USB 模式选择、目录选择、转换等待、导出后再验证，≥5 次人工介入；与「每年备份一次」的低频场景叠加，易用性风险高
3.5 现有架构适配性与成本（8 项逐条见附件 05）
  ① 可在现有架构扩展【技术上可行】album_scan 只读扫描/配对、album_index 索引、imageio-ffmpeg 媒体链可复用；但设备层与格式层是新领域，不宜塞进 LivePhoto_Backup.pyw
  ② 独立设备连接模块【观点】需要：COM/WPD 与 iOS 栈跟 Tk/WebView2 无耦合，应隔离
  ③ 独立格式转换模块【观点】需要：XMP 写入 + 容器拼接 + 长度计算 + 校验器应独立可测
  ④ 第三方依赖【技术上可行，尚未实测】现有 imageio-ffmpeg 可覆盖 remux/转码/抽帧；新增缺口 = XMP 读写库、HEIF/ISOBMFF box 写入能力、WPD COM 绑定、可选 iOS 栈。具体库选型【暂时无法确认】，须开发 AI 复核
  ⑤ 许可证与公开分发【已有官方依据 + 第三方合规声明】见 3.6
  ⑥ 联网【已有官方依据】核心处理可纯本地；但 Apple 设备 App 从 Microsoft Store 安装、iCloud 优化存储下载全分辨率原片、pip 安装依赖三处需联网 → 不能宣称「零联网」
  ⑦ 安装包体积【暂时无法确认】必然增加（HEIF/XMP/WPD 库，可能还有 iOS 栈），未实测不可给数值；可参考 V1.2 EXE 41.9 MB、V1.3 EXE 53.1 MB，但不外推
  ⑧ 维护成本【观点】高：iOS/Android 系统版本、厂商驱动、品牌相册差异、规范演进（1.0 已与旧 Microvideo V1 不兼容即为实证）
3.6 依赖与许可证风险（本节为最高优先级发现，详见附件 05）
  【第三方合规声明，非官方审计】现有 imageio-ffmpeg 包自身 BSD-2-Clause，但其 Windows ffmpeg 可执行为 `--enable-gpl --enable-version3` 构建（含 libx264/libx265），`ffmpeg -L` 显示 GPL-3.0-or-later。项目 V1.2/V1.3 已用 PyInstaller 打成单文件 EXE → 属再分发，GPL 源码义务**当前已存在**，不是本次扩展引入
  【项目自述】V1.0 报告 3.9/R13：项目无第三方依赖许可证清单、无隐私说明、无卸载说明、无 Git 仓库；README 定位「自用、无对外分发」
  【第三方合规声明】若新增 pillow-heif 做 HEIC 编码：其元数据 BSD-3-Clause，但预编译 wheel 捆绑 libheif/libde265(LGPL-3.0) 与 x265(GPL-2.0-or-later)，分发时引入 copyleft 义务；decoder-only 的 pi-heif 是社区规避路径，未经本项目评估
  【已有官方依据】pymobiledevice3 仓库明示 GPL-3.0 且提示闭源分发前阅读 FAQ；libusbmuxd LGPL-2.1；usbmuxd 的 Windows 分支 GPL-3.0；libimobiledevice 自述「未获 Apple 授权、赞助或认可」
  【观点】若维持「自用、不分发」，义务较轻；若 D1 裁定为对外发布，许可证合规与隐私说明应先于任何功能开发
3.7 真实设备验证需求（矩阵见附件 06）
  真实 iPhone（建议 2020 年后、HEVC .mov、含/不含 iCloud 优化存储两态）导出后逐项检查：双文件是否成对、Content Identifier 是否保留、HEIF/HEVC 是否被转码、全分辨率是否保住
  至少 2 个 Android 品牌 × 2 个 Android 版本 × 各品牌默认相册 App：Motion Photo 1.0 JPEG 版能否被识别与播放、HEIC 版能否识别、MTP 写入后是否自动入媒体库
  Windows 侧：WPD COM 枚举/写入、MTP 1.0 与 2.0 行为差异、拔线中断恢复
  【不建议实施】在上述验证完成前，不得对外宣称「支持 iPhone 直连导入」「支持 Android 动态照片」「兼容某品牌」
3.8 预计开发难度与建议优先级（【观点】定性排序，非工期估算、非开发授权）
  难度：本地「普通照片+视频」备用导出 低｜Motion Photo 1.0 JPEG 版（XMP+追加 MP4/MOV+文件名+长度计算）中｜HEIC 版（mpvd box + Padding=8 + HEIF 内 XMP）高｜WPD COM 写入与中断原子性 高｜iOS 设备层直连 很高｜全链路串通 最高
  建议优先级【交 ChatGPT 裁定】：P0 先决条件（非开发）＝补真实 iPhone HEVC .mov 样本、裁定产品定位、处理现有 GPL 合规、先解 V1.3 播放 3 FAIL；P1 本地双文件保留 + 备用导出（不碰设备层）；P2 Motion Photo 1.0 JPEG 版 + 独立校验器，真机播放另立验收；P3 Android MTP 写入（需设备矩阵）；P4 iOS USB 直连（最后或不做）
  ★ 任务书约束 6「不新增开发任务授权」：以上仅为排序建议，不构成开工许可
3.9 不建议实施的方案及原因（正反双方论据见附件 06）
  N1 pymobiledevice3 / libimobiledevice 直读 iPhone 照片库【不建议实施】：支持方（可读 Content Identifier、纯 Python）/ 反对方（GPL-3.0、Windows 需 iTunes/usbmuxd、iOS 17+ tunnel 与额外驱动、Apple 未授权该库、随 iOS 版本漂移、与免安装零维护冲突）
  N2 按旧 Microvideo V1 (`MicroVideoOffset`) 生成【不建议实施】：官方 1.0 已删除且须忽略
  N3 首版即做 HEIC 主图 Motion Photo【不建议实施（首版）】：须 mpvd box/ISOBMFF 写入、引入 GPL wheel、品牌兼容未知；且 V1.3 播放尚有 3 FAIL
  N4 覆盖/追加写入手机已有文件、或转换后自动删除原始文件【不建议实施】：MTP 1.0 不支持写已有文件，且无回滚、数据丢失不可逆
  N5 iCloud / 云端中转取原片【不建议实施（若维持纯本地定位）】：需联网与 Apple ID，与 README「零第三方服务、零联网」冲突；若 D1 改为对外发布可重评
